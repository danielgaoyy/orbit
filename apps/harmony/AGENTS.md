# `apps/harmony/` 局部工程规范

在遵守 [`../AGENTS.md`](../AGENTS.md) 与 [`docs/CLIENT_BRIDGE_ARCHITECTURE.md`](../../docs/CLIENT_BRIDGE_ARCHITECTURE.md) 的基础上，改动 HarmonyOS 客户端时必须满足：

1. **平台与 N-API 契约**：面向 HarmonyOS 7+（API 26，`ArkTS` + `ArkUI V2` Stage 模型），通过 `crates/orbit-ffi-ohos` 编译 `liborbit_ohos.so` 并与 `entry/src/main/cpp/types/liborbit_ohos/index.d.ts` 保持 Contract v2 JSON DTO 严格一致。
2. **严禁提交本机签名配置**：DevEco Studio 会在 `build-profile.json5` 写入本机绝对签名路径，提交前务必检查 `git diff`；CI 构建签名行为遵循 [`deploy/HARMONY_SIGNING.md`](../../deploy/HARMONY_SIGNING.md) 与 `scripts/strip-signing.py`。
3. **发版版本号规范**：同步更新 `AppScope/app.json5` 的 `versionCode` 与 `versionName`。
4. **Rust N-API 构建检查**：
   ```bash
   ./apps/harmony/scripts/build-rust-ohos.sh
   ```

5. **声明与 DTO**。运行 `bash scripts/check-ohos-dts-sync.sh --print-count` 检查 N-API 声明（既有导出顺序由脚本内的 `legacy_core_order` 固定，新导出自动追加在末尾，勿手工改写该列表）。运行 `cargo run -p orbit-ffi-ohos --bin export_dto_fixtures` 从 Rust view 生成样本，再运行 `node scripts/check-harmony-dto-contract.mjs` 核对 ArkTS 顶层字段。迁移期间支持 `model/OrbitTypes.ets` 和 `model/dto/*.ets`。
6. **流式性能回放**。仅 perf 构建可用，使用 `./apps/harmony/scripts/build-rust-ohos.sh --arch arm64 --features perf-hooks`。先订阅事件，再调用 `debugReplayStageDeltasJson(hostId, agentId, framesJson)`。录制数组上限 8 MiB、5000 帧，内置 `scripts/perf/fixtures/stream-500.json` 包含 100 轮、500 帧。回放按 40 帧/秒发出 `timeline_changed`，通过同一 host/agent 的常规 stage delta 接口拉取。回放结束后传入 `[]` 释放该会话的录制状态。普通构建调用返回 `perf hooks disabled`。
7. **本机 Hvigor 打包与 JRE 兜底**：macOS 本机未配置全局 JDK 时，`hvigorw` 的 `PackageHap` 需要 DevEco 内置 JBR：
   ```bash
   export DEVECO="/Applications/DevEco-Studio.app/Contents"
   export JAVA_HOME="${JAVA_HOME:-$DEVECO/jbr/Contents/Home}"
   export DEVECO_SDK_HOME="$DEVECO/sdk"
   export OHOS_NDK_HOME="$DEVECO_SDK_HOME/default/openharmony"
   export PATH="$JAVA_HOME/bin:$DEVECO/tools/ohpm/bin:$DEVECO/tools/node/bin:$DEVECO/sdk/default/openharmony/toolchains:$PATH"
   ```

8. **状态拉取与恢复**。Fleet、Host、Sidebar 和 Stage 的大载荷使用异步 N-API。Stage 按 `(host_id, agent_id)` 保存两个 revision 与窗口起点，`aux_unchanged` 时复用五个辅助字段。普通 `fleet_changed` 只刷新 Fleet 与 Briefing；收到 `resync_required` 时按可见 scope 重新拉取。SQLite 以单键 `orbit.drafts.v1` 保存整个草稿包，包内使用会话键 `${hostId}::${agentId}` 或新会话键 `draft::${hostId}`。详见[客户端桥接契约](../../docs/CLIENT_BRIDGE_ARCHITECTURE.md#harmonyos-n-api)。
9. **三语资源与静态子代理头像生成**。文案由 `node scripts/gen-harmony-strings.mjs` 从桌面三语词典 + `apps/harmony/i18n-keys.txt` + `apps/harmony/i18n-harmony-only.json` 生成，使用 `node scripts/gen-harmony-strings.mjs --check` 与 `bash scripts/check-harmony-i18n.sh` 校验（禁止遗留术语与裸英文）；子代理静态 SVG 头像与深浅底色由 `node scripts/gen-harmony-avatars.mjs` 从 `apps/desktop/src/lib/subagent-avatar.ts` 生成并使用 `--check` 校验。
10. **侧边面板、单模态与多形态壳层契约（PR-4）**：
   - `OrbitSidePanelStore` 按会话作用域（`${hostId}::${rootAgentId}` / `draft::${hostId}`）独立保存 `open`、`tabs`、`activeTabId`、`unseenTabIds`、`closedTabs`（LIFO 上限 10）与 `userDismissed`，经 Preferences 键 `orbit.harmony.v2.sidePanel` 以 220 ms 防抖持久化（LRU 上限 100 scope，基于 `flushSeq` 的脏标记保护确保同步/异步失败均可重试）；全局布局宽持久化于 `orbit.harmony.v2.sidebar_width_vp` 与 `orbit.harmony.v2.panel_width_vp`。
   - **数据隔离、无歧义身份与子代理路由铁律**：`components/panel/` 内所有面板视图只能读取显式 `tab.*`（`hostId` / `agentId` / `cwd` / `path` / `workspaceId` / `terminalSlot` / `gitStaged`）与 `scopeKey`，严禁回退读取全局 `selectedHostId` / `activeCwd`；路径比对与 tab/读写全链路仅用 `.trim().length === 0` 判空（ArkTS `nonBlankPath` 与 daemon `expand_host_path` / `authorize_*_cwd` 仅以 `.trim().is_empty()` 判空，`git rev-parse --show-toplevel` 通过 `strip_single_line_ending` 仅剥离单个平台记录结束符以保留目录名尾随空格及字面 `\r`/`\n`），严禁对非空 `cwd` 或文件 `path` 执行 `.trim()`（端到端保留 POSIX 目录与文件名尾随空格如 `repo `、`report.txt `，同时维持既有已注册目录授权边界），且按主机内完整规范化 cwd 精确匹配（严禁剥离 `req_seq >= latest_dispatched`）、物理隔离缓存 `git_diffs`（含 `source_req_seq`）、按 `cwd` 记录的完整目录身份映射 `(git_repo_root_by_cwd, git_repo_prefix_by_cwd)` 与目录身份代次 `git_cwd_identity_epoch`、统一派发序 `next_git_status_req_seq` / 在途状态请求表 `pending_git_status_requests` / 每 `cwd` 已接受状态序号 `git_status_seq_by_cwd` 与有效状态修订 `git_status_revision_by_cwd`、每槽终态错误修订 `last_git_diff_error_revision`、同 `cwd` 身份变更水位 `git_cwd_identity_watermark` / `git_cwd_root_set_seq` 以及工作树级 mutation 水印 `latest_mutation_watermark_by_repo_root`：`orbit-daemon` 全部状态查询、diff 查询（`GetGitDiff`）及仓库级/目录级变更处理器（Commit、Push、Create PR、Stash、Rebase、Stage、Unstage、ApplyHunk、Discard、ResolveConflict）均由 `resolve_git_scope` 下发向后兼容的主机实际解析符号链接后的规范物理 `repo_root` 与与请求目录完全一致的 `repo_prefix`（若请求子目录被变更删除则回退仓库根并精确推导相对前缀或 `None`，绝不将子目录误标为 `pending_git_status_requests` 按 UUID 绑定），纯读 `GitStatusResponse` 先核验 `effective_status_seq >= git_status_seq_by_cwd[cwd]`（反序旧查询整包丢弃且零副作用，`RpcError` 与断连清理在途查询；若在 diff 已确立身份但 `git_statuses` 仍为空时预身份状态查询以 `RpcError` 失败，则有界补发 1 次新代次核实查询，该核实查询失败则停止不循环）；若早于当前目录身份确立时派发的查询（`effective_status_seq <= git_cwd_identity_status_watermark[cwd]` 或 `origin_identity_epoch < current_identity_epoch`）返回冲突身份（涵盖已有旧身份热换仓以及冷启动由首次 diff 确立身份两种路径，如链接指向 B 且被 diff 确立后才收到采自 A 的旧状态），严禁把链接重绑回旧仓或清空已确认正文，仅在尚无较新核实查询在途时由 core 自动补发 1 次目标 `GetGitStatus` 重新核实；而作用于原工作树的 `GitMutationResult` 到达时严格区分「收到回执」与「在 daemon 实际采得快照」两类时点，并区分「仅存在仍在途重叠读取」与「已接纳过重叠读取」两类场景：现场分配高于此前已派发读取的完成代次 `completion_seq = next_git_status_req_seq += 1` 以拦截晚到的预写旧读；当在途期间同物理工作树已接纳过可能重叠的 `GitStatusResponse`（或工作树已接受序 `> `FfiGitReview.status_reverify_pending` / Swift & Kotlin `statusReverifyPending` 同步暴露）」——推高 `git_status_seq_by_cwd` 至 `completion_seq` 拒收迟到旧读并按原工作树合并派发 1 次 post-completion `GetGitStatus`（跳过投机性全仓 `GetGitDiff`），在复查响应到达前的整个等待期内**完整保留最后确认的 `git_statuses`、正文与 `diff_revision` 不清零、不退回旧快照**（页面即使在同槽 `diff_in_flight === true` 与状态复查并发在途期间，也经 `syncPostMutationGitReview` 优先保留并返回已确认正文与正修订而不清空缓存或启动超时清零，同时复用在途请求零重复拉取，直到复查 `GitStatusResponse` 抵达后才清除 `status_reverify_pending`、切换至权威最新快照并失效/重拉变化 diff；若该复查请求以 `RpcError` 失败或断连则及时复位 `status_reverify_pending`）；当仅有仍在途但尚未返回的重叠读取时则直接采纳回执并保留原 UUID 拦旧包同时合并补发 1 次 post-completion `GetGitStatus`，无重叠读取的常规写入保持 0 次额外状态请求（回执携带状态但未采纳时据实返回 `status_refreshed = false`）；仅当通过序与身份冲突校验的 `GitStatusResponse` 表明完整目录身份 `(repo_root, repo_prefix)` 发生实质变化（跨工作树根变更、同工作树内子目录前缀如 `one` -> `two` 变更，或非 Git 目录切换为 Git 仓库；同根且同前缀的普通刷新保持已确认缓存、`cwd_identity_epoch` 与 `git_cwd_root_set_seq` 不变，仅首次建根或身份切换时更新根建立序）时，立即递增 `cwd_identity_epoch`、推高身份水位与该 `cwd` 全部槽序号、清空旧目录 `git_diffs`、作废旧在途 UUID（对仍匹配新状态的槽以新 UUID 重发一次）并发出 `GitChanged`；收到 `GitDiffResponse` 时携带的 `repo_root`/`repo_prefix` 均保持局部态，直到身份水位、槽序号与 `(repo_root, repo_prefix)` 切换前守卫（同时核验 `req_seq` 与派发时 `status_seq_at_dispatch` 避免把同次刷新中晚于旧状态派发的新仓 diff 误杀为切换前回包）全部通过才写入映射（过期/被取代/切换前回包直接丢弃且绝不回写映射），若有效 `GitDiffResponse` 在热链接上早于新目录的 `GitStatusResponse` 揭示 `(repo_root, repo_prefix)` 变更，同步推进 `cwd_identity_epoch`、立即移出旧身份的 `git_statuses`/`git_status_identity_epoch_by_cwd`（绝不让旧仓库的干净状态冒充新目录状态）、记录 `git_cwd_identity_status_watermark = next_git_status_req_seq` 并在尚无新代次状态查询在途时由 core 自动派发 1 次目标 `GetGitStatus` 核实；若有效 `GitDiffResponse` 在冷 cwd 上首次确立 `(repo_root, repo_prefix)`（`existing_cwd_root` 与 `existing_cwd_prefix` 均为空），同样推进 `cwd_identity_epoch` 并锚定 `git_cwd_identity_status_watermark = next_git_status_req_seq` 与 `git_cwd_root_set_seq`，使常规冷启动同仓状态平滑采纳（0 额外查询）、冲突旧仓状态命中守卫不回绑且自动派发 1 次核实查询、无任何在途状态查询时自动补发 1 次 `GetGitStatus`（无需等待用户手动刷新）；跨 `cwd` 工作树关联**严禁按字符串路径包含猜测**，仅当 `a_cwd == b_cwd` 或双方均具备已记录的根且 `root_a == root_b` 时才属于同一物理工作树——从而统一真实目录、子目录与 POSIX 目录符号链接，同时 100% 隔离尚未收到首次状态的独立嵌套仓库（如 `vendor`）与尾随空格相邻仓库（如 `repo `）；对冷启动/尚无响应的同工作树子目录或符号链接，其 mutation 前发出的过期 `GitDiffResponse` 到达时由 `req_seq < latest_mutation_watermark_by_repo_root[repo_root]` 拦截拒绝（仅当该 `cwd` 尚无已知身份时登记），并按统一 `status_seq` 仅在工作树快照更新（`wt_seq > cwd_status_seq`）时同步状态并推进 `status_revision`、绝不用旧 mutation 快照回滚该 `cwd` 已收到的较新 `GitStatusResponse`，仅在该槽无存活在途请求且尚未由 `source_req_seq >= worktree_watermark` 的恢复回包确认、且较新状态仍匹配该槽时以新 UUID 重发一次；`dispatch_git_mutation_on_host` 在派发时记录发起当时的 `origin_repo_root`、`origin_identity_epoch` 与 `dispatch_seq`，收到 `GitMutationResult` 时按发起工作树物理根结算：若调用方 `cwd` 在变更期间已改指另一独立物理工作树（如链接 `A -> B`），仅对仍映射至原工作树 `A` 的 sibling 与 `latest_git_status_by_repo_root[A]` 执行缓存失效、状态刷新与通知，正常 resolve 写入回执，但严禁把已改指 `B` 的 `cwd` 重绑回 `A`、严禁清空 `B` 的缓存或覆盖 `B` 的状态、亦严禁对 `B` 发起例行全仓刷新（同工作树内子目录改指 `one -> two` 则保留 `two` 的 `repo_prefix`）；未改指其他工作树时无条件清空该物理工作树全部已缓存 `git_diffs`（绝不凭借未跟踪目录摘要 `<dir>/` 保活已删除文件的旧正文）、推高全工作树序号水位线并作废全部预变更在途请求，按完成代次 `completion_seq >= prev_seq` 以各 sibling 自身显示 `cwd`、权威 `repo_prefix` 与 `repo_root` 刷新受影响 `git_statuses`（同步推进 `status_revision` 并登记匹配 `status_identity_epoch`）并发出所有受影响 `cwd` 的去重 `GitChanged` 通知；被作废的在途请求按 `(norm_cwd, Option<path>, staged)` 全范围去重重发（同时覆盖单文件/目录 `Some(path)` 与全仓 `None`，仅在 `status` 非空且仍匹配时以新 `request_id`/`req_seq` 重发一次；已知 `repo_prefix` 按精确仓库根相对路径与 `staged` 模式匹配，`None` 按目标 `staged` 模式存在条目匹配，旧 daemon 缺失 `repo_prefix` 即 `None` 时保守在同 `staged` 模式仍存在条目时重发，干净或仅对侧模式存在条目时 0 重发；`dispatch_git_mutation_on_host` 检测到同槽已有存活在途请求时不再重复发起例行全仓拉取，断连/换代清空在途请求）；规范目录键 `canonical_git_cwd_key_for_flavor` 依据目标主机路径语义（`Posix` / `Windows` / `Unknown`）折叠冗余 `/` 与 `.` 段、仅基于该主机显式 `authoritative_home_dir` 展开 `~`，仅在明确 Windows 路径（`[A-Za-z]:` / `\\` 或已确认 Windows 主机）下将 `\` 转为 `/`（POSIX 及未知平台 `/` / `//` 路径绝不转换字面 `\`，未知平台保守保留前导 `//` 与单 `/` 独立且保持 `\\server\share` <-> `//server/share` 幂等，已确认 POSIX 主机将 `//` 折叠为 `/` 以对齐同 inode）；`GitReviewView` 返回向后兼容的 `(staged, diff_revision, diff_in_flight, status_revision, status_identity_epoch, status_reverify_pending, cwd_identity_epoch, last_diff_error_revision, last_diff_error_status_revision)`（`diff_revision` 仅该槽收到有效 `GitDiffResponse` 时严格单调递增；`status_revision` 仅该 `cwd` 真正接纳有效 `GitStatusSnapshot` 时单调递增并同步写入对应 `status_identity_epoch`，邻近文件 `GitDiffResponse` 与 `RpcError` 绝不递增它；`cwd_identity_epoch` 仅在 `(repo_root, repo_prefix)` 发生实质目录身份切换时递增；`diff_in_flight` 严格定义为该精确槽存在 `req_seq >= latest_dispatched` 且尚未收到成功 `GitDiffResponse` 或终态 `RpcError` 的存活在途请求——收到 `RpcError` 时按 `request_id` 结算失败的 pending diff、保留同槽较新 UUID，并对未被取代的失败请求记录 `(last_diff_error_revision, last_diff_error_status_revision = 当前 status_revision)` 并发出目标 `cwd` 的 `GitChanged`），`orbit-ffi-ohos` 的 `gitReviewJson` 支持可选第 4 参 `staged`（合并后总计 **240** 个 N-API 导出，含 PR-2 新增 `markAgentRead`），三参数旧包装器 `git_review` 在该规范 `(cwd, path)` 的两个模式槽间优先返回最新有效
